# Windows code-signing options without Azure

Research date: 2026-08-15. This note addresses public Windows distribution of a desktop application, not driver signing.

## Short answer

**Yes for Azure Artifact Signing itself:** Microsoft lists both a Microsoft Entra tenant ID and an Azure subscription as prerequisites, and its FAQ says the subscription must be paid (free, trial, and sponsored subscriptions are not supported). **No for Windows distribution generally:** a Microsoft Store MSIX submission and a conventional public-CA Authenticode certificate are viable alternatives that do not require an Azure subscription or Entra tenant.

## Options

| Path | What the recipient experiences | Publisher requirements and cost | Complexity / limits |
| --- | --- | --- | --- |
| **Azure Artifact Signing** | A publicly trusted publisher signature; a new application can still receive SmartScreen warnings while it builds reputation. | Entra tenant + paid Azure subscription, public-identity verification, and a supported geography. Basic is $9.99/month for 5,000 signatures; Premium is $99.99/month for 100,000. | Managed signing integrates well with CI. Identity validation is the schedule risk: Microsoft estimates **1–20 business days**, potentially longer for more documents. |
| **Microsoft Store, packaged MSIX** | Discover, acquire, install, and update through the Store. Microsoft signs the submitted package, so the publisher does not buy a public certificate. | A free Partner Center developer account. An individual account can use a personal Microsoft account, government ID, and selfie; it does **not** require an Entra tenant or Azure subscription. | Requires MSIX packaging, a Store listing, and certification. Microsoft says a new-app certification typically takes a few business days. This is the lowest-cost no-Azure public-trust route, but Store policy and packaging are real product constraints. |
| **Direct download signed by a public CA (Authenticode)** | Windows can identify a trusted publisher rather than an unknown/self-signed signer. SmartScreen reputation may still need time to build. | Buy an organization-validated (OV) public code-signing certificate from a CA trusted by Windows; perform the CA's validation and secure the signing key. No Azure or Entra requirement is inherent to this route. Microsoft names DigiCert and Sectigo as examples. | More release-secret/key-storage and vendor-management work than Artifact Signing. Timestamp each release so an expired certificate does not invalidate installed MSIX packages. Recent CA/B Forum rules require protected key storage; price and operating model vary substantially by CA. |
| **Self-signed MSIX / private trust** | The user or their IT administrator must first install and trust the signing certificate; otherwise installation fails. This does not solve public-download friction. | No certificate purchase. Suitable only for a controlled fleet where trust can be deployed first (for example, through Intune or Group Policy). | Appropriate for development, testing, or an organization-managed internal app. Intune itself requires an Intune subscription and Entra groups, so it is not a no-account public-distribution substitute. |

## Evidence and qualifications

### Azure Artifact Signing is an Azure product, not a Windows-wide prerequisite

The [Artifact Signing quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart) explicitly requires a Microsoft Entra tenant ID and Azure subscription. Its [FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq) further requires that subscription to be paid. Public Trust is currently available to organizations in the United States, Canada, the EU, UK, Australia, New Zealand, Japan, South Korea, Singapore, Switzerland, Norway, and Israel; individual developers are limited to the United States and Canada. Microsoft documents the 1–20-business-day public identity-validation timeframe in the [quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart#important-information-for-public-identity-validation). Current tier prices are in Microsoft's [SKU documentation](https://learn.microsoft.com/en-us/azure/artifact-signing/how-to-change-sku).

### Microsoft Store MSIX is the cleanest no-Azure alternative

For an MSIX Store submission, [Microsoft re-signs the package](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/publish-first-app); its own guide describes Store signing and the developer account as free. The [Partner Center onboarding instructions](https://learn.microsoft.com/en-us/windows/apps/publish/partner-center/open-a-developer-account) specify that an individual developer uses a personal Microsoft account, identity document, and selfie. A company may use either a personal Microsoft account or Entra work account, so Entra is optional rather than mandatory for that path. A company still needs business/contact verification.

Do not confuse this with listing an existing EXE/MSI in the Store: Microsoft says an **unpackaged** Store installer must already be signed by a certificate chaining to the [Microsoft Trusted Root Program](https://learn.microsoft.com/en-us/windows/apps/distribute-through-store/how-to-distribute-your-win32-app-through-microsoft-store). Only the packaged MSIX path eliminates the publisher's public-certificate purchase.

### MSIX is not the macOS-style sandbox for a full-trust desktop application

An MSIX package can contain a traditional Win32 application running at medium integrity (**full trust**), rather than an AppContainer application. Microsoft says such apps run with the same permissions as a standard desktop application and can access most system resources directly; `mediumIL` apps do not run in an AppContainer. Therefore a full-trust MSIX `codex-cost-meter` can read and update the current user's `.codex` directory with the same user permissions it has today. Do **not** package it as an AppContainer application: that is the restricted model and would require capability/file-access redesign. [Microsoft's capability guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations) and [containerization overview](https://learn.microsoft.com/en-us/windows/msix/msix-containerization-overview) distinguish these models.

MSIX nevertheless makes the present Windows scheduler implementation unsuitable for a Store release. The application currently registers a current-user task through `schtasks.exe`, starts `powershell.exe` during uninstall, and records the canonical executable path in the task XML ([ADR 0006](../adr/0006-use-current-user-windows-task-scheduler.md)). Microsoft's Store-packaging guidance warns against starting command utilities such as PowerShell or Cmd because they cannot run on Windows 10 S; it says this can block Store submission, whose apps must be Windows 10 S compatible. `schtasks.exe` is likewise a command-line utility, so the current command-tool approach needs an explicit Store-compatibility review and likely replacement before choosing this route. [Prepare a desktop app for MSIX](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-prepare)

The canonical path is also update-fragile: Microsoft documents that a package's installation path can change when it is updated. An [app execution alias](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/desktop-to-uwp-extensions#start-your-application-by-using-an-alias) is the supported way for other processes to start a packaged desktop app without its full path, but it must be proven with the actual Task Scheduler action before relying on it. A Store/MSIX implementation therefore needs a Store-compatible scheduling mechanism and an update-safe launch target; it is not a drop-in wrapper around the current `schtasks` XML. [Packaged-desktop compatibility guidance](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-prepare) documents the update-path risk.

### GitHub can host an MSIX, but cannot supply its Windows trust

**Yes, an MSIX can be attached to a GitHub Release and downloaded directly.** GitHub provides stable release-asset download URLs; this is MSIX sideloading, not a Store installation: the recipient downloads the `.msix` and opens it with App Installer. For a public install, Microsoft requires the package to be signed by a certificate already trusted by Windows—a public-CA certificate (including Artifact Signing) avoids certificate deployment; a self-signed certificate must be installed in the Local Computer trusted store on every device before installation. The Store re-signs only the package submitted and certified through the Store, so putting the same `.msix` on GitHub does **not** carry the Store signature or its warning-free install experience. [GitHub's release-asset URLs](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases), [Microsoft's direct web-install guidance](https://learn.microsoft.com/en-us/windows/msix/app-installer/installing-windows10-apps-web), and its [signing-options comparison](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options) establish that distinction.

An `.appinstaller` companion can add update checks for a directly hosted MSIX, but it does not remove the certificate requirement. The host must serve the required MIME types and support byte-range requests. Treat GitHub Release assets as the manual-download route; before using them as an App Installer update endpoint, verify those HTTP requirements on the actual asset URL, or use a purpose-configured HTTPS host. The former one-click `ms-appinstaller:` browser protocol has been disabled by default since December 2023; users must download and open the `.appinstaller` or `.msix` themselves. [Microsoft's distribution-path guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/choose-distribution-path) and [App Installer web-hosting requirements](https://learn.microsoft.com/en-us/windows/msix/app-installer/installing-windows10-apps-web) cover those constraints.

GitHub-native supply-chain features are still worthwhile, but solve a different problem:

* **Artifact attestations** generated in GitHub Actions record build provenance and can be verified with `gh attestation verify`; they do not make Windows trust or install the artifact. [GitHub documentation](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)
* **Immutable Releases** prevent published release assets and their tag from being changed and automatically create a release attestation. A technical user can run `gh release verify` or `gh release verify-asset`; this confirms a release asset matches GitHub's release record, not Windows publisher trust. [GitHub documentation](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) and [verification commands](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/verify-release-integrity)
* **SHA-256 checksum files** are a simple release-asset integrity check and can be produced in Actions, but users must choose to verify them; they do not identify a trusted Windows publisher or change SmartScreen.

So GitHub Releases are a good delivery and provenance channel for the existing direct-download path, once every Windows MSIX is signed and timestamped by a public CA. They are not a no-cost substitute for either public code signing or Microsoft Store distribution.

### Public-CA Authenticode remains a direct-download option

Microsoft explicitly recommends an OV certificate from a CA such as DigiCert or Sectigo for developers who are ineligible for Artifact Signing in its [Windows publishing guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/publish-first-app). That same guide warns that unsigned and self-signed direct downloads trigger strong SmartScreen warnings and can be blocked by enterprise policy. Microsoft also says timestamping is highly recommended; its [MSIX signing guidance](https://learn.microsoft.com/en-us/windows/msix/package/signing-package-overview) explains that a timestamp lets a package remain acceptable after the certificate expires.

Cost needs a quote, not a budget promise: Microsoft's publishing guide estimates OV at $150–300/year, while its [MSIX signing overview](https://learn.microsoft.com/en-us/windows/msix/package/signing-package-overview) gives $300–500/year. Issuer pricing is higher in current first-party examples: [DigiCert advertises from $44/month](https://www.digicert.com/signing/code-signing-certificates) on a 12-month auto-renewing subscription, and [Sectigo advertises from $536.25/year](https://www.sectigo.com/ssl-certificates-tls/code-signing) on its five-year option. The same vendors document FIPS-protected key storage/token or HSM requirements; this operational requirement is part of the route's real cost.

### Self-signing is enterprise/internal trust, not public trust

Microsoft's [Intune MSIX deployment guidance](https://learn.microsoft.com/en-us/windows/msix/desktop/managing-your-msix-deployment-intune) says a self-signed certificate must be trusted on every target device and is suitable only when all devices are Intune-managed and the app is never distributed outside the organization. Its more general [sideloading guidance](https://learn.microsoft.com/en-us/windows/application-management/sideload-apps-in-windows) likewise requires a certificate that the device trusts and certificate import before installation. That is useful for an existing managed fleet, but it transfers the warning/trust work to each user or administrator and is not a credible public-download UX improvement.

### Official user-help links

These links explain the platform safeguards; they are not a reason to disable them. Only use an override after confirming the release came from this repository and its published checksum matches. A managed device can prohibit an override, in which case the user must follow their organization's policy.

* **macOS:** Apple documents [how to safely open an app](https://support.apple.com/102445), including the **Open Anyway** exception in **System Settings > Privacy & Security** after a blocked launch. Apple explicitly advises this only when the user is certain the source is trustworthy and the software has not been tampered with; it is not a remedy for malware, revoked-certificate, or corrupt-app alerts.
* **Windows:** Microsoft's [SmartScreen documentation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation) explains that an unsigned direct download can show **Windows protected your PC** and requires an explicit **Run anyway** choice before it runs. Confirm the release and checksum first; do not disable SmartScreen, and follow organizational policy when it prevents continuation.
* **Build from source (macOS or Windows):** Follow this repository's [developer setup and build instructions](../../DEVELOPERS.md). The Rust project's [installation guide](https://doc.rust-lang.org/book/ch01-01-installation.html) covers `rustup` on macOS and Windows, the Xcode Command Line Tools linker on macOS, and Visual Studio build tools on Windows; use the repository's pinned toolchain and commands rather than substituting its generic examples.

## Recommendation

If the goal is a low-friction **public** Windows install without creating Azure or Entra infrastructure, choose one of two paths:

1. **Microsoft Store + MSIX** only when Store distribution is worth replacing the current command-tool scheduler and proving an update-safe scheduled launch. It has no signing-fee path and uses a personal Microsoft account for an individual publisher; it does not block normal current-user `.codex` access when packaged full trust.
2. **A conventional OV Authenticode certificate from a public CA** when the application must remain a direct download. Budget for annual certificate/key-storage cost and identity validation; sign and timestamp every release.

Keep self-signing only for local development or an already-managed internal fleet. Azure Artifact Signing can be reconsidered later if its CI convenience and roughly $10/month Basic tier justify establishing the required Azure account and completing verification.
