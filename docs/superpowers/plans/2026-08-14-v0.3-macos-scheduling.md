# v0.3 macOS Scheduling Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a safe current-user macOS LaunchAgent lifecycle, bounded status and circuit breaker, and self-uninstall to the existing Universal 2 binary.

**Architecture:** Keep one crate. `schedule` owns stable status and state transitions; `schedule::macos` owns the current-user LaunchAgent and filesystem/process boundary. Existing `update` behavior remains the mutation engine and exposes only a small failure classification needed by scheduled execution.

**Tech Stack:** Rust 2024, stable Rust 1.97.1, existing `clap`, `serde`, `serde_json`, `thiserror`, `time`, `rusqlite`, and standard-library filesystem/process APIs. No new runtime dependency.

## Global Constraints

- The application remains one Rust crate and one run-once binary; do not add a daemon or background thread.
- Add no empty Windows/Linux scheduler module and no speculative cross-platform scheduler trait.
- The LaunchAgent label is exactly `io.github.deinspanjer.codex-cost-meter` and its interval is exactly 300 seconds.
- Scheduled defaults are `--idle-minutes 15`, `--limit 500`, `--max-runtime 4m`, `--max-width 65`, `--title-metrics cost,total-tokens`, and explicit `--apply`.
- Persistent status contains no task IDs, titles, prompts, project paths, environment variables, arbitrary errors, or raw error chains.
- Scheduled success is silent; updater lock contention is a successful no-op that does not overwrite status.
- Three consecutive ordinary failures pause; one disk-full, incompatible-schema, or permission-denied failure pauses immediately.
- Status-write failure never changes the updater result and never emits arbitrary status-write error text.
- Tests must not register, boot out, or mutate a real user LaunchAgent.
- Use TDD for every production behavior and keep tests parallel-safe and focused on observable contracts.
- Before release, uplift durable content and remove this plan and its specification from the final tree.

- [ ] **Step 3: Implement stable codes and pure transitions**

Define the serialized result values exactly as:


Define `Status` with `last_run_at: Option<OffsetDateTime>`, `result`, a `u8` consecutive count, `paused`, and `remediation: String`. - [ ] **Step 4: Add the command grammar and lifecycle dispatch**

Add `Command::Schedule` and `Command::Uninstall`. Use nested schedule subcommands with install defaults exactly matching the global constraints. - [ ] **Step 5: Implement internal scheduled-run orchestration**

Before updating, read status. If paused, exit success silently. Otherwise invoke `update::run` with idle options and `apply = true`:

```rust
match update::run(codex_home, options) {
    Ok(_) => write_success_status_without_masking_update(),
    Err(UpdateError::LockBusy) => Ok(()),
    Err(error) => record_classified_failure_without_raw_metadata(error),
}
```

On successful update plus status-write failure, print exactly `update completed; schedule status unavailable` and return success. On update failure, emit only the stable result code and its allowlisted remediation; append only the fixed status-unavailable phrase when needed. Never call the existing arbitrary `error_chain` renderer from scheduled-run handling.
