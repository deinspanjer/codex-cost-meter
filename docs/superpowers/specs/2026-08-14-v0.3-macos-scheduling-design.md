# v0.3 macOS Scheduling Design

- Status: Approved under ADR 0004 standing authorization
- Date: 2026-08-14

## Scope

v0.3 adds the current-user macOS scheduling lifecycle to the existing Universal 2 binary:

```text
codex-cost-meter schedule install [options]
codex-cost-meter schedule status
codex-cost-meter schedule resume
codex-cost-meter schedule remove
codex-cost-meter uninstall
```

The operating system remains the scheduler. The application stays run-once and does not add a daemon, background thread, network service, runtime configuration framework, or scheduler abstraction for platforms that do not exist yet.

Installation schedules only automatic idle updates. It does not persist explicit thread IDs or title matches.

## Approaches considered

### Selected: standard-library LaunchAgent lifecycle

Generate the small property list directly with correct XML text escaping, write it atomically, and invoke the fixed macOS tools `/bin/launchctl` and `/usr/bin/id` with argument vectors. Keep pure construction and state-transition logic separate from the narrow filesystem/process boundary so tests do not mutate the user's real LaunchAgent domain.

This adds no dependency, matches the small single-crate design, and leaves later Windows and Linux scheduler implementations free to use their native concepts without forcing an early common trait.

### Rejected: add a property-list library

A property-list dependency would serialize the document safely, but the required document contains only a fixed dictionary and a string argument array. One tested XML text escaper is smaller than another runtime dependency.

### Rejected: application bundle scheduling APIs or a resident daemon

`SMAppService` would pull the project toward an application bundle and signing lifecycle before v1.0. A resident daemon duplicates launchd and contradicts the approved run-once architecture.

## Files and ownership

- `src/schedule.rs` owns schedule arguments, status transitions, the bounded status record, and platform-neutral orchestration used by the macOS implementation.
- `src/schedule/macos.rs` owns LaunchAgent paths and XML, fixed-tool process execution, current-user domain discovery, atomic installation, status inspection, removal, and executable deletion.
- `src/cli.rs` owns the public schedule and uninstall command grammar.
- `src/main.rs` dispatches interactive lifecycle commands and the internal scheduled run.
- `tests/schedule_cli.rs` covers only safe CLI boundaries that do not install a real job.

No empty Windows/Linux modules or multi-platform scheduler trait are added in v0.3.

## Installation contract

The LaunchAgent label is `io.github.deinspanjer.codex-cost-meter`. Its property list lives at:

```text
~/Library/LaunchAgents/io.github.deinspanjer.codex-cost-meter.plist
```

Installation resolves the current executable to its canonical absolute path. Moving or deleting that binary invalidates the installed job. The generated job uses:

- `RunAtLoad = true`;
- `StartInterval = 300`;
- `ProcessType = Background`; and
- a `ProgramArguments` array invoking the internal scheduled-run command.

The scheduled argument defaults are:

```text
--idle-minutes 15
--limit 500
--max-runtime 4m
--max-width 65
--title-metrics cost,total-tokens
--apply
```

`schedule install` accepts overrides for the idle threshold, limit, maximum runtime, maximum width, title metrics, optional fixed repricing cutoff, and Codex home. It does not expose `--apply`; scheduled execution always persists that argument explicitly. The five-minute interval is fixed for this milestone.

Installation creates the LaunchAgents directory when needed, atomically replaces the property list, ignores a missing prior job during `bootout`, and then bootstraps the new job in `gui/<uid>`. A bootstrap failure is actionable and leaves the property list available for inspection or retry.

The generated property list has no stdout or stderr file paths. Successful runs emit nothing. Fixed, privacy-safe scheduled errors may reach the macOS unified logging path, but the application creates no append-only log.

## Scheduled-run and circuit-breaker behavior

The LaunchAgent invokes an internal `schedule run` command that is not presented as a normal user workflow. It first reads the bounded status record. A paused schedule exits successfully without opening Codex storage.

Otherwise it executes the existing updater with the persisted idle options and `apply = true`:

- success records `success`, resets the consecutive-failure count, and remains silent;
- updater lock contention is a successful no-op that does not overwrite status while the winning updater is still running;
- an ordinary failure increments the consecutive-failure count and pauses on the third consecutive failure;
- disk exhaustion, a missing required SQLite column, or permission denial records a stable severe result and pauses immediately; and
- no on-disk error text, task metadata, path, ID, title, prompt, or project name enters the status record.

The stable result codes are `success`, `ordinary_failure`, `disk_full`, `incompatible_schema`, and `permission_denied`. A paused record retains the result that caused the pause. Remediation text is selected from fixed allowlisted strings by result code.

The existing updater error types gain only the source detail needed to classify permission and storage failures. This also completes the bounded v0.2 follow-up to preserve the I/O cause of an unreadable session index; it does not introduce a general error framework.

## Status record

macOS status is stored at:

```text
~/Library/Application Support/codex-cost-meter/status.json
```

It is a single overwrite-in-place JSON object containing only:

- nullable `last_run_at` as RFC 3339 UTC (`null` means never run);
- one stable result code;
- `consecutive_failures` capped at three;
- `paused`; and
- fixed allowlisted remediation text.

The record is serialized to a small temporary file, synchronized, permissioned `0600`, and atomically renamed. It is never append-only. A malformed status record fails safely with a fixed diagnostic rather than being guessed.

Failure to write status never changes the updater result. After a successful update, status failure prints only `update completed; schedule status unavailable` and exits successfully. After an update failure, the stable update result remains primary and a fixed status-unavailable suffix may be emitted.

`schedule status` reports whether the property list exists, whether launchd currently reports the label, and the bounded record or `never run`. It never prints LaunchAgent command output or plist contents.

## Resume, removal, and uninstall

`schedule resume` requires an installed property list, clears paused state and the consecutive-failure count, sets the stable result to `success`, preserves the prior last-run time (or `null` when never run), and leaves launchd registration intact.

`schedule remove` boots out the job when loaded, removes the property list, and removes the bounded status record. Missing job, property list, or status state is idempotent success. It retains the executable.

`uninstall` performs the same schedule removal and then unlinks only the canonical current executable. It does not recursively delete its parent directory or any Codex data. If schedule removal succeeds but executable deletion fails, it reports that partial outcome with the executable still present.

## Error and privacy behavior

Interactive lifecycle commands return concise typed errors with sanitized one-line output. Scheduled execution emits only stable codes and fixed remediation, never arbitrary error chains. Paths may appear in interactive installation/removal errors where the user needs them, but never in persistent status.

The following are severe for the circuit breaker:

- session-index or SQLite storage full;
- the required `threads` contract missing a required column; and
- a permission-denied source while opening the updater lock, SQLite database, or session index.

Other updater failures use the three-consecutive-failure rule. Status-storage failure is reported separately and cannot turn a successful title update into a failed update.

## Testing

All production behavior follows red-green-refactor TDD.

- Table-driven unit tests cover XML escaping, persisted argument order, status transitions, failure classification, failure-count saturation, immediate severe pause, explicit resume, and malformed status.
- Temporary directories exercise atomic property-list and status replacement, idempotent removal, status permissions where supported, and executable deletion without touching the real user's files.
- Process construction is tested through pure command plans or a private injected runner; tests do not register a real LaunchAgent.
- CLI integration covers parsing, safe `status` behavior in an isolated home, error sanitization, and fixed scheduled-run output.
- Existing update tests remain the source of truth for title mutation, locking, and dual-store recovery.

Tests remain parallel-safe. No global scheduler-state test is added to the normal suite. The full suite must remain a few seconds locally, and no new runtime dependency is expected.
