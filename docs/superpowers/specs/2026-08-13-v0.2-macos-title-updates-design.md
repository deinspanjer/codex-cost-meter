# v0.2 macOS Title Updates Design

- Status: Approved under the standing authorization in ADR 0004
- Date: 2026-08-13

## Goal

Add dry-run and explicit-apply title updates to the existing Universal 2 binary while preserving the prototype's root-only selection, dual-store persistence, high-water behavior, and recoverability. Add the approved width and metric-format controls without adding scheduling or another crate.

## Scope

v0.2 adds:

```text
codex-cost-meter update [explicit selection] [options]
codex-cost-meter update --idle-minutes MINUTES [options]
```

Explicit selection accepts repeatable `--thread-id` and `--match-title`; either or both may be present. It is mutually exclusive with `--idle-minutes`. Common options are:

```text
--apply
--codex-home PATH
--max-runtime SECONDS|MINUTESm
--max-width 65
--title-metrics cost,total-tokens
```

Idle selection also accepts `--limit` (default 20) and a fixed ISO date or timestamp through `--reprice-before`. Values that represent counts or durations must be positive. A repricing cutoff requires idle selection, must include a time zone when it contains a time, and cannot be in the future.

Dry-run is the default. v0.2 does not install scheduling, maintain scheduler status, uninstall itself, support Windows/Linux mutation, accept runtime price files, or add JSON output for updates.

## Chosen approach

Keep one crate. Add `rusqlite` with its bundled SQLite build so the self-contained binary does not depend on a separately installed CLI or dynamic SQLite version. Use the stable standard-library file-locking API; do not add a locking dependency.

Refactor reporting only enough to introduce one reusable context containing the rollout index and embedded price catalog. `report` and `update` both use it, so an update run scans rollouts and parses pricing once rather than once per selected root.

Add three focused modules:

- `title`: metric parsing, canonical suffix recognition, compact token rendering, and bounded composition.
- `session_index`: latest-valid-entry parsing and durable append/partial-line separation shared by reporting and updating.
- `update`: SQLite contract validation, selection, locking, report orchestration, dry-run/apply behavior, and typed failures.

The rejected alternatives are invoking an external `sqlite3` executable, writing custom SQLite bindings, copying the Python module structure, or inventing a transaction coordinator for SQLite plus JSONL.

## Selection and naming

Locate `state_5.sqlite` either directly under the Codex home or under `sqlite/`. Open it read-only for dry runs and read/write without create for apply runs. Use a bounded one-second busy timeout so transient Codex writes can clear without making interactive or scheduled failure handling stall.

Before any write transaction, verify that `threads` contains these required columns: `id`, `title`, `name`, `history_mode`, `updated_at`, and `first_user_message`. Extra tables, indexes, columns, and higher `user_version` values remain compatible. A missing table/column, corrupt database, unsupported file, lock, or permission failure returns a typed actionable error without panicking.

Build the rollout index once and accept only records classified as roots. Explicit IDs must identify both a SQLite row and a rollout root. A case-insensitive title substring searches SQLite title/name and the latest valid session-index name; zero or multiple matches are errors. Deduplicate roots selected through more than one explicit option while preserving first-selection order.

Idle selection:

1. reads roots idle at least the requested number of minutes, newest first;
2. excludes descendants;
3. applies the session-index high-water and repricing rules;
4. filters eligibility before applying `--limit`; and
5. checks the monotonic deadline before beginning each root report.

A normal high-water skip requires a valid canonical trailing suffix with the requested metric order, a title no wider than the requested maximum, and a latest index timestamp at least as new as the SQLite task timestamp. A fixed repricing campaign additionally requires the index timestamp to be at least the cutoff. Explicit selection always recomputes.

For a paginated row, prefer nonblank SQLite `name`. For a legacy row, prefer a nonblank SQLite title that differs from the first user message, then the latest valid session-index name. If neither supplies a user-facing name, normalize whitespace from the first user message, then SQLite title, then `Untitled`.

## Title composition

`--title-metrics` is a comma-separated ordered list containing one or more of:

- `cost`
- `total-tokens`
- `input-tokens`
- `output-tokens`

The default is `cost,total-tokens`. `all` expands to all four in the order above and cannot be combined with another value. Duplicates, unknown names, empty lists, and a maximum width that cannot hold a visible base plus the requested suffix are usage errors.

Render canonical segments as:

```text
$12.34
$12.34+
⇄1.4M
⇥1.2M
↦200K
```

Cost uses the whole-tree known cost and gains `+` when the complete estimate is unavailable. Total tokens are whole-tree input plus output; input and output metrics use their corresponding whole-tree counters. Token counts use an integer below 1,000 and one decimal with trailing `.0` removed for `K`, `M`, and `B` units.

Join the base and segments with ` · `. Recognize and remove only a contiguous canonical metric suffix at the end, including the Python cost-only suffix, before appending the new requested suffix. Similar text in the middle of a user title remains untouched. Count Unicode scalar values, not UTF-8 bytes. When truncation is required, end the visible base with `…`; never truncate a metric suffix.

## Mutation and recovery

Hold one nonblocking process lock at `<codex-home>/thread-cost-title-updater.lock` from before the SQLite/session-index snapshot until all writes finish. Interactive contention is a typed failure; the v0.3 scheduler may later map it to a successful no-op.

Compute every selected update before starting a write transaction. With `--apply`:

1. update each selected row's SQLite `title` and `name` in one transaction and commit;
2. append one JSON object per update to `session_index.jsonl` with a shared current UTC `updated_at`;
3. if the existing final record lacks a newline, write a separating newline first; and
4. flush and synchronize the index before reporting success.

SQLite and JSONL are intentionally not cross-store atomic. A database failure rolls back without appending. An index failure after commit returns failure; the unchanged/older latest valid index entry keeps the root eligible, so a rerun repairs both stores. Malformed index records are ignored for high-water purposes while the latest valid record remains authoritative.

Human output prints one sanitized single-line `id: old -> new` record per proposed update and a concise dry-run or applied summary. It can still disclose local task metadata, so the user guide retains the privacy warning. No default persistent log is introduced.

## Tests and validation

Use temporary Codex homes and parallel-safe tests. Add only behavior-class coverage:

- table-driven metric parsing, ordering, compact values, suffix replacement, Unicode width, and too-small widths;
- latest valid index selection, malformed/unknown records, truncated final-line repair, append durability errors, and missing index behavior;
- root-only explicit and idle selection, unique title matching, deduplication, history-mode base names, filtering before limit, high-water/reprice behavior, and deadline stopping;
- dry-run immutability and successful dual-store apply;
- unrelated SQLite schema additions and higher `user_version` accepted, required-column/corrupt/read-only/locked stores rejected before unsafe writes;
- simulated disk-full/index-write failure followed by a successful repair rerun;
- concurrent updater exclusion; and
- terminal-control sanitization and non-panicking errors for on-disk input.

Prefer compact table-driven unit tests in the owning module plus one update CLI integration file. Do not create a fixture per edge case, a custom test framework, or scheduler tests. Focused warm tests should remain below one second and the full suite should remain a few seconds. Validate with focused tests during TDD, then `just check` and `just package`.
